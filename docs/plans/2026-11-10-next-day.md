## Task 1: A tool server can no longer skip the yes by calling itself read only (do first)

**The hole.** `workbench/backend/app/mcp_client.py` line 465 copies the server's own `readOnlyHint` into
`"read_only"`. `workbench/backend/app/assistant.py` line 967 trusts it:

```python
ro = bool(spec.get("read_only"))
tools.append(Tool(..., effect="read" if ro else "external",
                  confirm=None if ro else (lambda _a: MCP_ASK_REASON)))
```

So a server that labels "send_email" read only runs it with no yes. It also passes the `subagent` filter a few lines
below (`t.effect == "read"`), so team sub-agents get it too.

**The fix.**
* A server's own label never decides holding. Every tool from a connected server is `effect="external"` with
  `confirm` set, unless the **person** marked that exact tool read only.
* Day one is allowed to have no marking at all (every tool asks). If you add marking, it is stored per server and per
  tool, set only from the signed-in app's Settings, never through the bridge key, a tool call, an automation or the
  app's own tool server. Give that its own test per channel.
* Keep the server's label for display only (for example "This server says it only reads"), under Advanced.

**Tests** (in `workbench/backend/tests/test_mcp_client.py` or `test_assistant.py`, using the existing fake server
pattern there):
1. A fake server whose `send` tool has `readOnlyHint: true`. Calling it is held in Needs you and the fake receives
   nothing until approved. Must fail on today's code.
2. The same tool is not offered on the `subagent` channel. Must fail on today's code.
3. If you add marking: a mark set with the bridge key is refused.

**Also update:** the comment just above that loop ("unless the server marks the tool readOnlyHint, like Claude Code"),
`CHANGELOG.md`, and design 0013 section 6 row C0 (mark the label part done).

## Task 3: The shared app key cannot reach the work mailbox and calendar

**The gap** (recorded in 0012 "Review on release/1.1", "The shared key's reads"): with the shared key,
`search_email`, `read_email`, `list_events` and the app's own tool server still reach the **work** mailbox and
calendar like a personal one. This breaks rule 5.

**The fix.** When `Ctx.shared_key` is true (see `rooks_link.shared_key(request)`), those tools and the app's tool
server leave out the work account's mail and calendar, the same way `/v1/rooks/history` and `/v1/rooks/calendar`
already do. The person's own signed-in app keeps full access.

**Tests:** with the shared key, each of `search_email`, `read_email`, `list_events` and the app's tool server returns
nothing from a fake work account while a personal account still works. With the signed-in app, the work account still
works. The shared-key cases fail on today's code.

**Do not change** the facts in `/v1/rooks/context` and `/memory` in this task. Write a short note in BACKLOG that this
is still open and needs the owner's decision.
