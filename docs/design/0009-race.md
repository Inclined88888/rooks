# 0009: Race. Several candidates try one coding task, tests score them, you pick the winner.

Status: design record, 2026-11-08. Builds on phase 1a (`sdk.py`, `permissions.py`, headless mode) and 0004 sections 8 and 9 (approvals hold in the background). Terminal first; the app shows the race and takes the pick (section 7). Tests first (section 9), all against the scripted fake model in `tests/fakes.py`; no real key.

## 1. What this is

You give Rooks one coding task. Three candidates (or as many as you ask for) work on it at once, each in its own private copy of your project, each on the model and approach you chose. Each must prove its work: a test that fails on your project as it is today, then the change that makes it pass. Rooks does not take its word for that: a judge runs the new test on an untouched copy and expects failure, then on the candidate and expects a pass; then every candidate's tests run on every candidate, and the project's own test command on each. You get a scoreboard of measured numbers, read the diffs, and pick one. Only then does your real project change, through the normal edit path, approvals and one `/undo`. The others are kept for a while.

**What is new, honestly.** Codex offers several attempts of a task in its cloud, on one model. Claude Code runs parallel agents in git worktrees, but nothing judges them by running tests. Checking a change with tests the agent wrote is a known research idea. Rooks adds the combination, local: any mix of the 18 providers, local models and your own Claude Code or Codex plan in one race; a judge that executes the tests with fail-first proof instead of reading claims; one spending cap and the usual permission rules over all of it; the real project untouched until you pick. The proof is necessary, not sufficient: a test that fails before and passes after can still be weak, which is why the other candidates' tests, the project's suite and your reading of the diff are part of the score.

## 2. Words

Terminal: `/race "task" [--n 3] [--models a,b,c] [--briefs smallest,robust,fastest] [--time 15m] [--auto]`, `/race show [N]`, `/race pick N`, `/race drop`. From the shell `rooks race "task" ...`; headless `rooks race -p --output-format json|stream-json`. Before it starts: "3 candidates will try this task, each on its own copy of this folder. Nothing here changes until you pick one. Cap for the whole race: $1.00 and 200,000 tokens." `--models` takes provider/model pairs as `/model` names them (`anthropic/claude-sonnet-5-5`, `ollama/qwen2.5:7b`, `claude-code`, `codex`); one model means all use it; none means the session's. A brief is a short approach note in the candidate's instructions: `smallest`, `robust` (edge cases, the project's style), `fastest`, or free text in quotes. `words.py`: `/race` joins the Checks group as "several candidates try one task on their own copies; tests score them; you pick".

## 3. How a race runs (`rooks_code/race.py`)

1. **Copies.** In a git repository each candidate gets a detached worktree of `HEAD` under `.rooks/race/<race>/c1..cN`, plus `base` for the judge; your uncommitted changes go into every copy (tracked diff applied, untracked files copied, ignored files left out). Otherwise a plain copy without `SKIP_DIRS`. Dependency folders (`node_modules`, `.venv`, `target`) are linked from the real project, read-only under the sandbox. The worktree's `.git` points at the real repository, which is read-only to the candidate, so it cannot commit; its work is its working tree.
2. **Candidates.** Each is a normal `Agent` with its own settings (`root` = its copy, its provider and model), `RunLog`, `Toolbox(root=copy, sandbox=settings.sandbox)` and `ChangeSets`, in its own thread. No MCP servers, no learning (`learn=False`: a race writes no memory, skills or chat history; three candidates would save three contradicting facts), no Room link. Its instructions are the normal system prompt for its copy plus the brief: the task, "first write a test that fails on the project as it is, in its test style and folder; then make the change; do not commit; end with a short summary". A `claude-code` or `codex` candidate runs through `delegate.py` in its copy behind the same gate; headless it is refused at start (exit 2), as `sdk.run` refuses delegates today.
3. **One cap, shared.** The race may spend what one session may: the session's `max_usd` and `max_tokens`. Each candidate's own limit is the cap divided by N; one that finishes under its share releases the rest to the others. A `SharedBudget` (a `Budget` whose `check` sums every candidate's receipts) stops a candidate before the call that would cross either limit: "stopped: cost cap". A model with no known price makes that candidate's cost "unknown", never a guess; the dollar cap cannot be enforced for it, the token cap still is, and the start screen says so.
4. **Time.** `--time` (default 15 minutes) per candidate. At the limit its cancel event is set, its running command ended, and it is "stopped: time"; a model call in flight ends at the provider's timeout. The judge's test runs use the project's test timeout (`lint_test.py`, 120 s, configurable).
5. **Approvals.** Candidates run under the same permission rules, folder trust and sandbox as a normal run, through one gate: the race UI takes their questions one at a time and asks you, each naming its candidate ("Candidate 2, Claude Sonnet, wants to run: pytest -q"). `a` approves that exact command or file for every candidate in this race, since every copy is the same project. Deny rules refuse in every mode. Headless, every question is denied at once, like any headless step; `--yes` and rules work as for `rooks -p`. A candidate's request never waits in Needs you: candidates have no conversation link; the race posts one card of its own (section 7).

## 4. The judge

Runs after the last candidate ends, outside the sandbox, as you, and never asks a model anything.

* **New tests** come from the candidate's diff, not its answer: added or changed files matching the project's test patterns (`test_*.py`, `*_test.py`, `tests/**`, `*.test.*`, `*.spec.*`). No test in the diff: "no proof".
* **Fail-first proof.** The candidate's test files are copied onto a fresh `base` and the project's test command runs on them alone; expected: failure. Then on the candidate; expected: pass. A test that passes on `base` is **proves nothing**; one that fails on its own candidate is **does not pass its own test**. Both lose the proof points and the words appear on the scoreboard.
* **Cross tests.** Every candidate's test files run on every other candidate: "others' tests 2/2".
* **The project's own tests.** The configured command (`lint_test.py`'s detection, or `test_command` in `rooks.toml`) runs on each candidate: pass, fail with a count, or "not run" with the reason.
* **Order.** A full pass is proof held, every other candidate's tests pass, the project's tests pass. Full passes first, then more others' tests passed, then the smaller diff, then the lower cost. The order is a convenience; the numbers are the result.

## 5. Scoreboard, pick, keep, drop

```
Race: make add() handle negative numbers         3 candidates · 4 m 12 s · $0.31 · 61,204 tokens
#  Candidate                    Proof           Others' tests  Project tests        Diff    Files  Tokens  Cost   Time
1  Claude Sonnet · smallest     fails first ✓   2/2            48 passed            +12 -3  2      18,400  $0.11  1 m 40 s
2  qwen2.5:7b (local) · robust  fails first ✓   1/2            48 passed            +41 -9  3      30,100  $0     3 m 05 s
3  GPT-4.1 mini · fastest       proves nothing  2/2            47 passed, 1 failed  +9 -2   1      12,700  $0.04  0 m 58 s
/race show N for a diff and its test output · /race pick N applies one · /race drop removes them all
```

Every number is measured: tokens and cost from receipts, time from the clock, diff and files from the copy, tests from exit codes and output. "unknown" is printed where a price is unknown.

`/race pick N` applies the winner through the normal edit path: one approval for the whole set, shown as the full diff ("Apply Candidate 1's changes: 2 files, +12 -3"), after every file passed the deny rules and the project hook (a file a rule never allows refuses the whole pick and names it; nothing partial). The files are snapshotted into one change set labelled "race: <task>", so `/undo` puts them all back. A file that changed in the real project since the race began is refused and named. `--auto` picks unasked only when exactly one candidate has a full pass; otherwise it says why and leaves the race for `/race show`, which prints a candidate's diff, test output and receipt path. Copies stay until `/race drop`, or until the next `/race` here asks to remove them; `drop` removes and prunes the worktrees. The record, redacted like a receipt, is `.rooks/race/<race>/race.json`.

## 6. Headless

`rooks race -p` runs the race with no input; `sdk.race(...)` does the same in process and returns a `RaceResult` (`candidates`, each a headless `Result` plus its scores; `picked`; `exit_code`). Exit codes as `sdk.py`: 0 when the race finished and, with `--auto`, a winner was applied; 1 when no candidate finished or `--auto` found no single full pass; 2 setup; 3 when any step was denied. New stream events in `schema/headless.schema.json`: `race_start`, `candidate_start`, every ordinary event carrying `"candidate": N`, `judge` (`candidate`, `check`: proof, cross, project; `passed`, `detail`), `scoreboard`, `race_end`. Keys, tokens, emails and phone numbers are hidden as in every headless line.

## 7. App parity

The terminal runs races in v1; the app shows them and can pick. The terminal posts `POST /v1/rooks/race` at start and `POST /v1/rooks/race/{id}` on each change; the app keeps a job of kind `race` on the Jobs board ("Race: <task>", detail "3 of 3 running", then status `waiting`, needs `pick`). The card shows the scoreboard as a table, each row opening to its diff and test output, and two buttons, "Use this one" and "Use none". `POST /api/jobs/{id}/pick` records the pick; `GET /v1/rooks/race/{id}` returns it to the terminal, which polls while waiting and applies with the normal approval (which also waits in Needs you when the session is linked). Who may pick follows the approvals rule exactly: the signed-in person or the Terminal access token; the app's own key in `app.json`, readable by any command on this computer, gets the approvals' own refusal. The card says "Picked here; the terminal applies it."

## 8. Security

Same rules, more copies. A candidate's file tools are confined to its copy (`Toolbox._path`); its commands run in the command sandbox with only its copy and the temp folder writable, so the real project, the other copies and `.git` are read-only to it (the temp folder is shared, as in a normal run). A candidate cannot approve anything: it holds no UI, no conversation id and no token beyond what a normal run has, and the pick route refuses the app key. The judge runs only the project's own test command, as you, with no extra rights. Where no sandbox exists (Windows, `sandbox = "full"`) the approval line says so, as today, and the file tools' confinement still holds. Receipts and `race.json` are redacted; keys reach a candidate only as they reach a normal run.

## 9. Tests

In `tests/test_race.py`, `test_race_e2e.py` and the backend's `tests/test_race_card.py`. Where one fails on today's code only because the feature is missing, it says so; the others also guard code that exists now.

1. `test_race_makes_one_copy_per_candidate_plus_base_from_the_working_tree`: an uncommitted edit is in every copy. Fails today: no `race.py`.
2. `test_a_candidate_cannot_write_outside_its_copy`: the fake model asks for `write_file ../c2/x` and `../../calc.py`; both refused, nothing written. Guards `Toolbox._path`; the race part fails today.
3. `test_a_candidates_command_cannot_write_the_real_project_or_another_copy` (Linux with `bwrap`): `echo x > ../../calc.py` exits non-zero, file unchanged. Guards the sandbox binds.
4. `test_the_judge_marks_a_test_that_passes_on_base_as_proves_nothing`: a candidate adds `assert True`; the scoreboard says so and ranks it last. Fails today: no judge.
5. `test_the_judge_runs_every_candidates_tests_on_every_candidate`: two candidates, one weaker; counts match real pytest exit codes.
6. `test_the_race_shares_one_cap_and_stops_the_candidate_that_would_cross_it`: caps set so the third call crosses; one says "stopped: cost cap", the total stays under the cap.
7. `test_a_stalled_candidate_is_stopped_at_the_time_limit`: a sleeping command; "stopped: time".
8. `test_a_candidate_cannot_answer_its_own_question_or_pick`: a candidate's command POSTs an answer and a pick with the app key; both refused, the question still waits. Guards today's approvals rule and the new route.
9. `test_headless_race_denies_every_question_exits_3_and_every_stream_line_validates`: fails today on the unknown events.
10. `test_pick_applies_through_a_change_set_and_undo_restores_everything`: files match the candidate after the pick; `/undo` restores all; a deny rule on one file refuses the whole pick.
11. `test_a_race_writes_no_memory_skills_or_chat_history`: with a fake app, nothing reaches remember, skills or conversation routes.
12. `test_the_app_shows_a_race_job_and_only_the_person_or_terminal_token_can_pick` (backend). Fails today: no route.
13. `test_readme_and_help_describe_race_in_plain_words`: `/race` in `words.COMMANDS` and the README, no URLs or ids.

## 10. Limits and open questions

An editable install that imports the real project would make a copy's tests test the wrong code; v1 puts the copy first on the import path, and the proof step reports the rest (such a test fails on both). Merging two candidates is not offered: pick one, run again. The Room (rooks-try) is not used for copies in v1; the command sandbox is.
